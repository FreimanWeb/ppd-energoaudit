# Цифровая модель энергоаудита ППД

Прототип цифрового энергоаудита насосных агрегатов ППД. Он объединяет паспортные
данные, телеметрию и расчёт по выездному замеру. Расчётные формулы соответствуют
Методике энергоаудита (формулы 7–47); ограничения и допущения выводятся в UI.

## Быстрый старт

**Windows, одной кнопкой:** `START.cmd` в корне проекта. Скрипт сам поставит uv и
(через winget) Node.js, установит пакеты, соберёт БД, запустит API и интерфейс и
откроет браузер. Автотесты — `TESTS.cmd`. Linux/macOS/Git Bash — `./run.sh`
(тесты — `./run.sh test`). Подробно — `START_HERE.txt`.

По шагам (нужны uv и Node.js 22.12+):

```bash
scripts/dev.sh setup    # uv sync --all-packages и npm ci
scripts/dev.sh data     # собрать БД из файлов проекта (≈1 мин при первом запуске)
scripts/dev.sh start    # API :8000 + интерфейс http://127.0.0.1:5173 (Ctrl+C — стоп)
scripts/dev.sh test     # Ruff, pytest, типы и тесты фронтенда, сборка
```

В PowerShell — `.\scripts\dev.ps1 setup|data|start|test`. Те же проверки
запускает GitHub Actions (`.github/workflows/ci.yml`).

БД собирается из файлов репозитория: паспорта `config/plants`, выгрузки ТИ/ТС
`data/telemetry/scada`, годовые выгрузки «Измерения» `data/telemetry/exports`.
API при запуске проверяет набор файлов и догружает новые выгрузки сам, поэтому
шаг `data` нужен только для того, чтобы не ждать импорта при первом старте.
Пересобрать БД с нуля: `scripts/dev.sh data --rebuild` (или `make data`).

## Структура монорепозитория

В одном репозитории находятся:

- `apps/api/src/ppd_audit/` — Python-ядро, работа с данными и FastAPI; imports `ppd_audit` сохранены;
- `apps/api/tests/` — проверки ядра и API;
- `apps/web/` — React + TypeScript + Vite, npm workspace `@ppd/frontend`;
- `shared/` — общие изображения оборудования и словарь потерь;
- `config/` и `data/` — общие конфигурация и данные, независимо от приложения.

Корень не является Python-приложением: `pyproject.toml` задаёт uv workspace,
общие dev-зависимости и настройки проверок. `uv.lock` и `package-lock.json` —
единые lock-файлы Python и JavaScript.
Расчётное ядро остаётся в пакете API, без преждевременного выделения в `packages/`.

Главная страница React — мониторинг всех объектов (`#portfolio`). Карточки
показывают последний доступный УРЭ, его историю и изменение, отдельно — свежесть
измерений. Общий DatePicker задаёт конец графиков; по умолчанию выбрана сегодняшняя
дата (`Europe/Moscow`). Доступны сутки, 7, 30, 90 и 180 дней. Шкала всех карточек
охватывает выбранный период целиком, включая пустой участок после последних
измерений. Выбор исторической даты меняет историю графиков, а последние KPI
сохраняют собственные даты измерений.
Переход с карточки открывает обзор объекта с временными графиками
(`#timeline`): вся станция или выбранный агрегат, общий курсор и масштаб,
периоды 7/30/90 дней и произвольный диапазон. `start`/`end` сохраняют выбранную
историю в URL; «Последние данные» возвращает последний доступный период.
Главная не требует выбора снимка. «Схема и участки» (`#overview`) показывает
всю станцию: сумму мощностей и расходов на общий момент, УРЭ как отношение сумм,
сценарную годовую оценку и общую технологическую схему. Выбор отдельного НА здесь
не используется. Его КПД, УРЭ, паспорт, рабочая точка и карта до БГ находятся в
«Машинном блоке». Прогноз закачки расположен в разделе «Скважины».

Под условной схемой статьи сгруппированы в «Машинный блок и обвязка до БГ» и
«От БГ до устьев скважин»; штуцирование входит во вторую группу. Статьи потерь показаны с линиями привязки к точкам
оборудования и водоводов. Под статьями скобками обозначены группы участков.
В общей схеме машинный блок представлен номинальными потерями, отклонением КПД и суммарной составляющей «Насос–БГ»;
во внешней сети — трение, местные сопротивления и штуцирование. Доли считаются
от электрического ввода. Граница графа — устья после штуцеров: мощность на БГ
является промежуточным итогом, а трение в стволах находится за границей графа.
В API этому представлению соответствует `network.operator_balance`; физическая
декомпозиция `network.items` и расчёты сценариев сохраняются отдельно.

Мониторинг — прототип для ожидаемой телеметрии с фиксированным шагом 2 часа.
Для реальных объектов он использует фактические записи SQLite.
Изолированный `demo-ppd` содержит два работающих синтетических НА и шесть скважин;
его ряды добавляются идемпотентно и не заменяют реальные данные. В расчётах
суточные энергия и объём дают суточный УРЭ, синхронные мощность и расход —
интервальный УРЭ. Пропуски остаются разрывами. Суточные значения не дробятся
на двухчасовые, КПД насосов не усредняется в станционный показатель.

В «Машинном блоке» и «Режимном расчёте» суточные измерения показаны отдельно
от расчёта выбранного режима. Без суточных W и Q_сут фактический УРЭ отсутствует:
отношение мощности к подаче отображается только как «По режиму».
Суточный УРЭ не оценивается цветом относительно расчёта по отдельному снимку давления.
Годовой сценарий явно показывает принятую наработку, её источник и тариф;
это экстраполяция режима, не измеренный годовой баланс и не достигнутая экономия.
Непригодный режим сохраняет исходные суточные данные, но не открывает экономические выводы.

Рост УРЭ свыше 10% относительно предыдущей точки той же базы служит предварительным
сигналом для проверки условий работы, а не диагнозом неисправности. Правила
сопоставимости режимов и пороги требуют согласования с аналитиком.

Read-only API: `GET /monitoring/objects` и
`GET /objects/{object_id}/timeline` с необязательными `aggregate_id`, `start`, `end`.
Карточки мониторинга сначала получают KPI через `/monitoring/objects?include_history=false`,
затем графики загружаются отдельно через `/monitoring/history?history_days=30&history_end=YYYY-MM-DD`.
До загрузки истории на месте графиков показаны skeleton; смена периода или даты не перезагружает KPI.
История объекта в API `timeline` по умолчанию заканчивается последней доступной
датой. Карточки используют дату из DatePicker. Архивные данные явно отмечаются;
автоматического обновления по таймеру нет.
Для оценки свежести время без offset предварительно считается `Europe/Moscow`.
Часовой пояс и привязку двухчасовой сетки следует согласовать при получении новой
выгрузки.

React-интерфейс включает разделы: обзор, режимный расчёт,
телеметрия, прогноз закачки, CRM по агрегатам и скважинам, карта потерь,
рабочая точка, мероприятия, подключение объекта и формулы. Технологическая схема ППД
встроена в обзор; hash `#scheme` также открывает обзор. Дополнительный раздел
показывает источники данных. Боковая панель содержит фильтры воды/НГДУ, объект,
агрегат, календарь пригодности и общий момент измерения. Сначала в сайдбаре расположены рабочие разделы, ниже — параметры анализа;
на desktop параметры прокручиваются отдельно.
Объект, агрегат, дата, момент и режим сохраняются в query-параметрах URL
(`object`, `aggregate`, `day`, `timestamp`, `mode`), раздел — в hash. Ссылку
можно открыть в другой вкладке или передать коллеге; обновление страницы и
Back/Forward восстанавливают выбранный контекст. При изменении селекторов
текущая запись history обновляется без добавления шага на каждый выбор.
При смене агрегата внутри объекта дата и момент сохраняются, в том числе при
диагностике НА в машинном блоке. Если подходящего снимка нет, интерфейс сообщает об этом
и сохраняет выбранное время без подстановки другого расчёта.

Нажатие на столбец карты потерь открывает конкретную статью с параметром `inspect`.
В общей карте переход ведёт на соответствующий участок: машинный блок,
трубопроводы или скважины. Ссылка сохраняет контекст анализа, обновление и Back/Forward
восстанавливают статью. Сворачивание графика не меняет выбранную статью и её мощность;
для недоступной в другом режиме составляющей показывается причина, а не другая потеря.

Графики построены на Visx и D3 с общей палитрой и SVG-rendering. В машинном блоке УРЭ и КПД
используют компактные панели; диагностические показатели КПД видны сразу,
дополнительные ориентиры УРЭ раскрываются по кнопке. Пояснения доступны при наведении и фокусе на значениях. КПД показывается
в процентах, отклонение от номинального — в процентных пунктах.
Карточка параметров выбранного НА связана с ним короткой линией, обходящей
трубопроводы; при недостатке места карточка расположена под схемой. Паспорт
раскрывается нажатием на заголовок. Меню показателей ведут к связанным источникам,
формулам, потерям и мероприятиям, сохраняя выбранный момент измерения.
Телеметрия использует общий курсор и диапазон для всех графиков; выбор точки
открывает расчёт только при наличии соответствующего снимка.
CAPEX мероприятий отделён от годовой экономии.
Единый календарь показывает пригодность данных цветом дней;
фильтры воды и НГДУ находятся перед выбором объекта.

Интерфейс и API используют одно Python-ядро и общие `services`: каталог и исходные
данные, прогноз, кривые насоса, экономика, требования к данным и типографика формул.
React получает расчётные значения через API. Новый объект регистрируется из YAML
без изменения кода; раздел «Готовность данных» содержит требования и шаблон.
Создание и редактирование паспортов через браузер не предусмотрено.

Для разработки нужны Node.js 22.12+ и `uv`. Установка из корня монорепо:

```bash
uv sync --frozen --all-packages
npm ci
```

Одна команда запускает API и frontend; при выходе одного процесса второй
останавливается, Ctrl+C останавливает оба:

```bash
npm run dev
```

Для раздельного запуска доступны `npm run dev:api` и `npm run dev:web`.

Frontend открывается на `http://127.0.0.1:5173`, API — на
`http://127.0.0.1:8000`, OpenAPI — на `http://127.0.0.1:8000/docs`.
Vite направляет `/api/*` в FastAPI, поэтому для локального запуска отдельная
настройка CORS не требуется. Этот запуск предназначен для локальной разработки. Авторизация
задаётся переменной окружения `PPD_APP_PASSWORD`. Без настроенного пароля вход свободный.
API выдаёт подписанную HttpOnly cookie `ppd_session` сроком на 8 часов; logout
удаляет её. Для нескольких backend workers задайте одинаковый
`PPD_SESSION_SECRET` длиной не менее 32 байт. Для HTTPS задайте
`PPD_COOKIE_SECURE=1`. Reverse proxy должен перезаписывать `X-Forwarded-Host`
реальным внешним host; Vite делает это автоматически.

API использует `telemetry.sqlite` в корне; альтернативный путь задаётся
через `PPD_DATABASE_PATH`. При старте API подготавливает БД (справочники и
выгрузки АСУ ТП); отключить это можно `PPD_SKIP_DATA_PREPARE=1`. Интерфейс не
подставляет выездной расчёт при отсутствии измерений.

```bash
npm run typecheck
npm run test:frontend
npm run build
uv run --frozen --all-packages pytest
npm run test:e2e
```

Browser-проверки поднимают отдельные FastAPI/Vite на портах 8181/5181 и
8191/5191, создают временную SQLite и собственные CSV/XLSX источники. Рабочие
данные не изменяются. Установите Chromium через
`npm exec --workspace @ppd/frontend -- playwright install chromium` либо задайте
`PLAYWRIGHT_CHROMIUM_EXECUTABLE` путём к установленному Chromium.

React-сборка сохраняется в `apps/web/dist`. Для публикации React нужен сервер,
который раздаёт файлы и направляет `/api/*` в backend; dev proxy в сборку не входит.
Работающий экземпляр: https://ppd.nie1ix.ru. Релизы размещаются отдельно в
`/opt/ppd-energoaudit/releases`; nginx и сервис `ppd-energoaudit.service` используют
symlink `/opt/ppd-energoaudit/current`. SHA исходников хранится в `RELEASE_SHA`.
Перед переключением релиза сохраняется backup SQLite из `/var/lib/ppd-energoaudit`.
Конфигурация сервера и пароль остаются в `/etc/ppd-energoaudit.env`.
Для нового релиза устанавливайте API через `uv sync --frozen --package ppd-audit --no-dev`,
а nginx направляйте на `apps/web/dist` внутри релиза.
Эта реорганизация сама по себе не меняет конфигурацию работающего production-сервера.

## Текущее состояние данных

- `telemetry.sqlite` в корне — локальная SQLite-БД приложения. Она хранит объекты,
  НГДУ, паспорта, уточнения и нормализованную телеметрию. Файл намеренно не
  коммитится: при необходимости он передаётся отдельно.
- `config/plants/*.yaml` — начальные паспорта и исходные выездные замеры. После
  перезапуска API новые объекты добавляются и в уже заполненную БД; существующие
  паспортные версии не перезаписываются. Оба режима расчёта читают оборудование из SQLite.
- `data/raw/ntu` — symlink на внешнюю папку «НТУ цифровая платформа». Он не переносим
  между рабочими местами и не является обязательным для работы приложения.
- `data/telemetry/exports` — годовые выгрузки «Измерения» (xls в zip) по КНС-54,
  КНС-97/2 и КНС-ОПУ за 25.10.2025–25.10.2026. Колонки сопоставлены с тегами
  модели в `config/scada_tags.yaml` (`measurement_exports`); в пересекающемся
  периоде годовая выгрузка заменяет ряды ТИ того же тега (значения совпадают).
- `data/reference` — справочные материалы заказчика (бенчмарки насосов и ЭД,
  алгоритм критичных параметров НА с рабочими характеристиками ЦНСн) и их JSON
  (`make reference` пересобирает его из xlsx); справочная шероховатость труб —
  `config/hydraulic_reference.yaml`.
- `data/toir` — журналы выявленных дефектов 1С ТОИР по агрегатам
  (сопоставление — `config/toir.yaml`).
- Сверка гидравлики с данными и отчётом — `docs/hydraulics-reconciliation.md`.
- ДНС-7с оставлена как legacy-верификационный пример. Ссылки на её Excel-файлы сейчас
  битые, поэтому в текущей SQLite-БД для ДНС-7с нет телеметрии. Не используйте
  `make ingest`, пока исходные файлы не будут получены заново.

### Временная база, гидравлические группы и неполные данные

- `power` — мощность измеренного режима; `power_daily_reported` — отдельное число
  из суточного отчёта с неподтверждённой базой усреднения. Оно не заменяет мощность
  снимка. Средние `W/T` за часы работы и `W/24` за календарные сутки вычисляются
  отдельно и показаны отдельно. Для `W/T` нужна подтверждённая наработка.
- При наличии канала часового расхода снимки предлагаются на пригодных измеренных
  точках Q. Расход другого времени суток и среднее по всем точкам дня не подставляются
  в снимок. Разрыв или плохое качество ряда не превращаются в более редкий «полный»
  ряд для интегрирования. Удержание состояний давления/мощности не означает нового замера;
  возраст состояния показан в расчёте.
- `technical_places` в описании объекта задаёт именованные гидравлические группы,
  `aggregates[].technical_place_code` — принадлежность агрегата. Идентификаторы НА
  уникальны внутри объекта; ссылки на незаданные группы отклоняются до записи в БД.
  КНС-97 остаётся одним объектом: НА-1/НА-3 относятся к `kns97`, НА-2 ПР — к `kns97pr`.
  Давление БГ и условная схема разделены по группам. Геометрия сети КНС-97/2
  в `config/network.yaml` относится к `kns97pr`, не ко всему объекту.
- Единицы давления не определяются по величине числа. Неподтверждённые единицы,
  неизвестные коды качества и неоднозначные заголовки моточасов сохраняются в исходных
  данных, но исключаются из зависимых расчётов. Неидентифицированный канал давления
  хранится как `pressure_unassigned`, не перезаписывая основное давление на выкиде.
- Отсутствующий паспортный КПД не заменяется типовым: фактические H, гидравлическая
  мощность, КПД агрегата и режимный УРЭ доступны при достаточных измерениях; расчётный
  УРЭ и потери относительно номинала остаются недоступными.
- Реестровая сеть с месячными расходами и разновременными давлениями — сценарий,
  не одновременный измеренный баланс. Интерфейс показывает периоды и условность
  трактовки исходных «атм». Исследования скважин сохраняются историей, без выбора
  произвольной последней плотности в качестве свойства жидкости.
- Ядро один раз выбирает годовую наработку: `regime.t_year`, затем
  `reference.t_year`, иначе явно сценарные 8760 ч. Заданный ноль не считается
  отсутствующим значением. Сводка, карта потерь, мероприятия, прогноз и трассировка
  используют эту же базу. Суточный `W/Q_сут` сохраняется отдельно: годовые потери
  выбранного режима экстраполируются из его `P_эл/Q` и `Q·T_год`, не из суточного УРЭ.

### Характеристики насосов и проверка уставок

- `curve_qh` хранит точки `[Q, H]` в м³/ч и метрах, `curve_qeta` — `[Q, η]`
  с КПД в долях. Вводятся вручную по проверенному источнику, не импортируются из отчётов.
- `pump.curve_source` описывает происхождение (`manufacturer`, `engineering`,
  `experimental`, `unverified`), ссылку `reference`, привязку `model`, обороты
  `speed_rpm`, частоту питания `frequency_hz`, признак `verified` и примечание.
  Наличие точек само по себе не подтверждает применимость к установленному насосу.
  Метаданные сохраняются в версиях паспортов БД (схема 18).
- Опорные H и η вычисляются квадратичным МНК только внутри соответствующего
  диапазона исходных Q; это не точная интерполяция через все точки.
  Экстраполяции, обрезания недопустимого КПД до 100% и подстановки эталонного H
  вместо недоступной характеристики нет. Несовпадение модели/оборотов блокирует расчёт.
- Для ОПУ и НА-2 ПР КНС-97 вручную внесены точки ЕРБ 2499-2023,
  приложение Д, таблица Д.1 (A-2026-027). Формулы Рамиля A-2026-042 —
  аппроксимации этой информационной нормативной таблицы, не независимый эксперимент
  и не паспорта установленных насосов. Все четыре записи — `engineering`,
  `verified: false`, обороты/частота источником не подтверждены. Для НА-3 ОПУ
  справочная АЦНС 180-1422-1 оставлена непривязанной: в книге обозначение (-1),
  но напоры базового варианта. Номинальные параметры и измерения не подменены.
- Уставка имеет статус `validated`, `proposal`, `infeasible`, `unavailable`
  или `no_change`. Для проверки нужны ПЧ, подтверждённая характеристика и её
  частота питания, допустимая целевая точка без экстраполяции и согласованность
  текущего измеренного H/КПД с характеристикой. Учитывается остаток МНК;
  неподтверждённый эксплуатационный допуск не выдумывается.
- Для непроверенной/недостижимой точки частота, целевой УРЭ и эффект — `null`;
  без давления БГ неизвестна и цель. Для проверенной модельной точки УРЭ
  использует её КПД, эффект — разность мощностей × ту же годовую наработку.
  Это отдельный расчёт от потенциала ΔW_дрос исходного режима; эффекты могут
  различаться. Положительный прогноз уставки строится только для `validated`.
  Закон подобия и неизменный КПД привода — явные допущения, не команда управления.

### Детализация потерь и журнал оборудования

- «Показатели» содержат выбранный режим, отдельный суточный факт при наличии
  исходных данных, КПД, УРЭ и существенные отклонения. Динамика КПД показывается
  по телеметрии. Полный разбор выбранной потери сюда не переносится.
  Паспорт доступен в «Источниках», полная диагностика — в «Режимном расчёте»,
  годовые оценки и их формулы — по ссылке «Годовая оценка».
- В «Машинный блок → Карта потерь» показаны общий итог и одно физическое
  распределение: ПЧ, двигатель, передача, насос и перепад мощности насос–БГ.
  До выбора составляющей подробного разбора нет; мероприятия и альтернативное
  причинное разложение не дублируются на этой странице.
  Рядом с итогом видны электрический ввод, гидравлическая мощность на БГ и
  доля общих потерь; у выбранной составляющей — её доля электрического ввода.
  Неизвестная доля не подменяется нулём.
- Выбор открывает краткий разбор только этой составляющей. «Расчёт и источники»
  ведёт в «Данные и методика → Формулы» (`#formulas`) с формулой, подстановкой,
  входными значениями и источниками; ссылка обратно сохраняет выбор и режим.
  Старые адресные ссылки на причинные потери открывают соответствующий разбор
  без второй карты. Физические и причинные потери нельзя складывать.
  Формулы и числовые подстановки оформляются тем же KaTeX-компонентом, что
  формулы методики: с дробями и индексами; длинные выражения прокручиваются
  внутри блока. Исходные выражения и расчётные значения в API сохраняются.
- В подробном расчёте доступны «По оборудованию» и «По причинам».
  Причинный баланс КНС содержит номинальные потери, отклонение КПД и две части
  перепада насос–БГ; для перекачки его граница — выход насоса, без выдуманной БГ.
  Износ, неоптимальная подача, загрузка ЭД и вязкость открываются отдельно как
  составляющие отклонения КПД и не прибавляются повторно к общему балансу.
  Для КНС исходная модель не выделяет эти частные причины: сохранён известный
  общий результат, распределение остаётся неизвестным. Знаки отклонений сохраняются.
- В подробном разборе потерь подтверждения источников и допущения собраны
  в свёрнутую сводку «Уточнения и допущения (N)». Одинаковые пояснения внутри
  одного статуса показываются один раз; значения, затронутые расчёты и ссылки
  на конкретные параметры остаются доступны после раскрытия.
  На краткой карте неизвестные составляющие обозначены «Нет расчёта», а не нулём.
  Недостающие данные видны в выбранном разборе, противоречия баланса и
  нераспределённый остаток — рядом с общим итогом. В «Готовности данных» сохранён полный список.
- Машинный блок до БГ рассчитывается независимо от сетевого сценария.
  При неизвестном КПД оборудования известный общий итог сохраняется, неизвестные
  составляющие остаются `null`, остаток показывается как нераспределённый.
  Перепад насос–БГ без высот и сечений не доказывает диссипативные потери.
- Ниже БГ граница операторского баланса — устье после штуцера: трубопроводы
  содержат трение и местные сопротивления, скважины — штуцирование. Ствол за этой
  границей. Геометрия, распределение расходов и сопротивления требуют подтверждения.
- В «Данные и методика → Журнал оборудования» (`#equipment-journal`) записываются
  только изменяемые параметры насоса, ЭД, передачи или ПЧ, включая кривые насоса.
  Для записи нужны дата действия, основание, источник, автор и вид сведений:
  документированные данные либо оценка специалиста. Оценка остаётся допущением;
  сам факт ремонта не подтверждает КПД. Номинальный КПД и Q–η не равны измеренному
  КПД текущего режима.
- Форма заполняется значениями на выбранную дату действия; поля расположены в одну
  колонку. «Сохранить» открывает подтверждение с полными названиями и значениями
  «было → стало». До подтверждения запись не создаётся; отмена сохраняет черновик.
  Неизменённые поля не публикуются, изменение только формата числа не считается
  изменением. Очистка числового поля записывает неизвестное значение, не ноль.
  Без фактических изменений кнопка «Сохранить» неактивна; пояснение рядом показывает,
  есть ли несохранённые изменения. Исправления только даты или источника учитываются.
  При замене отдельно показываются параметры нового оборудования и очистки;
  при исправлении можно изменить только дату или основание сведений.
- Имена, обозначения и единицы всех 22 параметров определены в едином справочнике
  `apps/api/src/ppd_audit/equipment_parameters.py`. Форма, подтверждение и история
  используют его, а не отдельные списки сокращений.
- `Действует с` — фактический момент изменения, `Записана` — время ввода на сервере.
  Поздний ввод изменения насоса не откатывает двигатель или более поздние значения.
  Оборудование собирается независимо по параметрам на момент снимка, а не начало суток.
  История показателей использует ту же сборку.
- Исправление явно ссылается на исходную запись; исходные сведения остаются в журнале.
  Исправление даты меняет период применения. Совпадение даты и параметра само по себе
  не означает исправление: неоднозначные записи и конкурирующие правки дают 409,
  черновик сохраняется до явной загрузки/проверки актуального журнала.
- При замене неуказанные характеристики только этого узла становятся неизвестными,
  а не наследуются от прежнего оборудования. Для насоса обязательны модель и тип,
  для ЭД — модель. Автоматические очистки не считаются подтверждёнными параметрами.
- Полная форма ручного замера и публикация целого паспорта удалены. Сохранённые
  замеры доступны в архиве, не выбираются автоматически и не меняют телеметрию.
  Исходные выездные режимы остаются источниками расчёта.
- API-поле `equipment_override` по-прежнему задаёт несохраняемый сценарий;
  он не подтверждает применимость характеристики.
- «Готовность данных» доступна и без успешного аудита: для каждой проблемы показаны
  причина, затронутые расчёты и действие. Незаполненный КПД передачи не заменяется 1.

## Подключение нового объекта

1. Создайте `config/plants/<id>.yaml` по шаблону из «Готовности данных» (`#onboarding`).
   Поле `id` должно совпадать с именем файла без `.yaml`; для нового реального объекта
   обязателен `ngdu`. Заполните паспорта агрегатов и, если есть, выездной `regime`.
2. Перезапустите API: `npm run dev:api` либо общий `npm run dev`. Новый объект,
   его агрегаты и начальные паспорта будут зарегистрированы при загрузке каталога.
   Уже существующие паспортные версии и правки имени объекта сохраняются.
3. `operator_visible` по умолчанию равен `true`. Значение `false` скрывает исторический
   объект из операторского каталога и мониторинга, но не удаляет его данные.
   Этот флаг синхронизируется из YAML при перезапуске.
4. Телеметрия подключается отдельно через существующий импорт/API. Без неё в портфеле
   указано отсутствие измерений, а выездной расчёт доступен только при заполненном `regime`.
   Для внешней сети используется `data/armits/<id>.json`, для условной схемы —
   `config/topology/<id>.yaml`. Наличие сети определяется по данным, не по списку кодов
   объектов в интерфейсе. Отсутствующие источники не заменяются демонстрационными.
   После изменения файлов сети или схемы также перезапустите API.
5. Полный сетевой сценарий не ограничен кодами станций. В `data/armits/<id>.json`
   поле `object_id` должно совпадать с объектом; нужны геометрия `segments` и список
   `wells` в существующем формате снимка. Начало сети задаётся `root_node` либо
   `station_nodes`; запись станции в `config/network.yaml` задаёт приоритетные
   `station_nodes` и `technical_place_code` для обоих сетевых представлений.
   У объекта с несколькими гидравлическими группами группа сети обязательна:
   геометрия другой группы не применяется к выбранному НА. Сценарий требует
   пригодного режима КНС, давления БГ и КПД привода; циклы и неоднозначные соединения
   отклоняются. Неизвестные подключения не становятся подтверждёнными:
   синтетические соединения перечисляются в ограничениях расчёта.
   `is_synthetic: true` обозначает синтетическую геометрию независимо от кода объекта.

## Независимая установка API

API можно установить и запустить без frontend:

```bash
uv sync --frozen --package ppd-audit
npm run dev:api
```

По умолчанию приложение использует `telemetry.sqlite` в корне. Для другого файла
задайте `PPD_DATABASE_PATH` перед запуском API. Если БД отсутствует, приложение
создаст её, перенесёт паспорта из `config/plants/` и импортирует доступные
стандартизованные выгрузки ТИ/ТС и годовые «Измерения».
`PPD_SKIP_DATA_PREPARE=1` отключает подготовку, а `PPD_SKIP_SCADA_TELEMETRY=1` —
только импорт телеметрии. Инженерные отчёты автоматически не импортируются.

## Режимы интерфейса

- **Анализ** — расчёт по телеметрии SQLite за выбранные сутки. Сначала выбирается
  пригодный режимный снимок: устойчивая пара `p_вх`/`p_вых`, согласованная с
  положительной мощностью. Если данных недостаточно, приложение показывает причину,
  а не подставляет выездной расчёт.
- **Выезд** — статичный расчёт по YAML-паспорту и выездному замеру. Календарь,
  телеметрия и индикаторы её наличия в этом режиме не используются.
- **Просмотр телеметрии** — графики исходных точек за выбранный период без расчёта KPI.

В режиме «Анализ по телеметрии» `🟢` означает, что хотя бы у одного агрегата объекта
есть записи телеметрии, `⚪` — что их нет. Это не оценка пригодности конкретной даты.

## Модель данных

SQLite содержит:

- объект, НГДУ, тип воды и ветку расчёта;
- технические места и агрегаты;
- версии паспортов насоса, двигателя и трансмиссии;
- неизменяемую историю исправлений паспортов и происхождение отдельных параметров;
- ручные контрольные замеры, отдельно от телеметрии;
- временные ряды `p_вх`, `p_вых`, `p_БГ`, мощности, расхода, энергии, наработки и
  других метрик;
- временные значения, требующие уточнения.

`p_вх`, `p_вых` и `p_БГ` хранятся как события изменения: строка появляется только
при новом значении, а до следующего события действует последнее записанное значение.
Отсутствие строки не означает отсутствие данных. Мощность дискретна с шагом 30 минут;
пропущенный слот также означает сохранение предыдущего значения. SQLite хранит только
исходные события, а расчёт восстанавливает действующее состояние в выбранном окне.

Для КНС `p_БГ` — станционная метрика напорного коллектора. Она не заменяет
`p_вых` конкретного насоса: в расчёт допускаются только физически корректные снимки
с `p_вых > p_вх` и, при наличии `p_БГ`, с `p_вых > p_БГ`.

## Источники и ограничения

Тестовые временные ряды в текущей БД относятся к КНС-10, КНС-54, КНС-ОПУ и КНС-97.
Наличие записи не означает, что по ней возможен полный расчёт: требуются паспорт,
подача, мощность и согласованные давления. Режим «Выезд» доступен и для объектов
без телеметрии, если YAML содержит измеренный режим.

Файлы `…расчет.xlsx` и текстовые отчёты остаются источниками исторической сверки,
но не требуются для обычного запуска приложения. Их пути могут ссылаться на внешнюю
папку данных и потому не считаются частью переносимого прототипа.

## API

Дополнительные источники можно задать через `PPD_CRM_DIR`,
`PPD_DOWNTIME_DIR`, `PPD_SCADA_TAGS_PATH`, `PPD_NETWORK_DIR`, `PPD_NETWORK_CONFIG`;
без них используются каталоги проекта (`data/network`, `config/network.yaml`).
Полные схемы запросов и ответов доступны в OpenAPI.

- `GET /auth/session`, `POST /auth/login`, `POST /auth/logout` — состояние входа,
  вход с `{ "password": "..." }` и выход.
- `GET /catalog/objects` — каталог объектов с наличием телеметрии; прежний
  `GET /objects` сохраняет свой контракт.
- `GET /objects/{object_id}/telemetry?aggregate_id=&start=&end=` — события и
  подготовленные ряды за период включительно (`start/end`: `YYYY-MM-DD`).
- `GET /objects/{object_id}/aggregates/{aggregate_id}/calendar?month=YYYY-MM`
  — пригодность суток.
- `GET /objects/{object_id}/aggregates/{aggregate_id}/forecast?start=&end=&period_days=&horizon=`
  — история и прогноз; период 1/7/30 суток, горизонт до 3660 периодов.
- `GET /objects/{object_id}/crm/runs`, `/crm/runs/{code}`, `/crm/fact`
  — прогоны, прогнозы агрегатов и фактическая закачка.
- `GET /objects/{object_id}/crm/well-runs`, `/crm/well-runs/{code}`,
  `/crm/well-runs/{code}/graph` — месячные прогнозы скважин и граф связей.
- `GET /objects/{object_id}/crm/well-runs/{code}/monthly?well=` — выбранный
  месячный ряд, временное окно и отметки простоев.
- `GET /objects/{object_id}/well-downtime`, `/clarifications?aggregate_id=`
  — простои скважин и временные паспортные значения.
- `GET /objects/{object_id}/network?eta=` — разводящая сеть: трение в водоводах
  по реестру трубопроводов, перепады до устья и на штуцерах по карточкам АРМИТС,
  годовые потери; `eta` — КПД насосной установки (по умолчанию номинальный).
- `POST /objects/{object_id}/aggregates/{aggregate_id}/loss-detail` (`loss` — ключ
  статьи из `shared/loss-labels.json`) — подробности статьи карты потерь: формула,
  исходные величины, состав (трубопроводы, скважины, оборудование), проверки.
  Открывается кликом по столбцу на картах потерь (`#loss-detail`).
- `POST /objects/{object_id}/aggregates/{aggregate_id}/recommendations` —
  14 критериев «Таблиц по КНС», бенчмарки насосов и ЭД, рабочая область,
  дефекты 1С ТОИР с причинами по алгоритму НА (`#recommendations`).
- `GET /reference` — справочные материалы (`#reference`).
- `GET /objects/{object_id}/scheme-pressures?day=&timestamp=` — давление каждой
  ветки на общем моменте; отсутствующие снимки не заменяются чужими значениями.
- `POST /objects/{object_id}/aggregates/{aggregate_id}/field-trip-audit`
  — выездной аудит из YAML, без выдуманного телеметрического снимка.
- `POST /objects/{object_id}/aggregates/{aggregate_id}/working-point`, `/measures`
  — характеристики и экономика; контекст `source: telemetry|field_trip`,
  для телеметрии обязательны `day` и `timestamp`.
- `GET /objects/{object_id}/aggregates/{aggregate_id}/onboarding`
  — требования, полнота паспорта и шаблоны.
- `GET /objects/{object_id}/aggregates/{aggregate_id}/equipment?at=...`
  — оборудование, собранное из базового паспорта и журнала на момент времени.
- `GET`/`POST .../equipment-journal` — журнал изменений. POST принимает `component`,
  `effective_at`, `expected_revision`, словарь `changes` с ключами вроде `pump.eta_nom`,
  `reason`, `evidence`, `source`, `author`, необязательный комментарий.
  Для исправления передаётся `supersedes_id`; исходный набор изменяемых полей сохраняется.
  Ответ содержит `parameters`: справочник ключей, полных названий, обозначений,
  единиц, типов полей и допустимых диапазонов для интерфейса.
- `GET .../manual-measurements` — только архив сохранённых ручных замеров.
  Старые POST `/equipment` и `/manual-measurements` удалены.
- `POST .../loss-detail` — контекст анализа и `key` составляющей; необязателен
  сетевой `scenario`. Контекст принимает `measurement_id` для выездного режима
  и несохраняемый `equipment_override`.
- `GET`/`POST .../data-requirements` — требования; POST с `with_regime: false`
  не требует пригодного замера и позволяет заполнить оборудование заранее.

- `GET /health` — healthcheck.
- `GET /objects` — объекты из SQLite.
- `GET /objects/{object_id}/aggregates` — агрегаты объекта и наличие телеметрии.
- `GET /objects/{object_id}/aggregates/{aggregate_id}/dates` — доступные даты
  и дата первоначального выбора.
- `GET /objects/{object_id}/aggregates/{aggregate_id}/snapshots?day=YYYY-MM-DD`
  — пригодные режимные снимки выбранных суток.
- `GET /objects/{object_id}/topology` — описание технологической схемы либо
  явно обозначенная типовая цепочка по реальным агрегатам.
- `POST /objects/{object_id}/station-summary` — общая сводка без выбора НА.
  Тело `{ "source": "telemetry" }` выбирает последний общий момент точных пар
  мощности/расхода всех НА; явные `day`/`timestamp` не подменяются. Неполные данные
  дают `complete=false` и `null` вместо частичных станционных сумм. `network`
  объединяет общую сеть только при совместимых режимах; `annual_basis` описывает
  основание сценарной годовой оценки.
- `POST /objects/{object_id}/aggregates/{aggregate_id}/snapshot-audit`
  — аудит точного снимка; тело `{ "day": "YYYY-MM-DD", "timestamp": "..." }`.
  Ответ содержит показатели, качество, источники параметров, расчётное основание
  годовых оценок и статьи потерь. Для непригодных режимов статьи потерь не выдаются.
- `POST /energy/audit` — расчёт по переданному `ObjectSpec`.
- `POST /objects/{object_id}/aggregates/{aggregate_id}/audits` — расчёт по окну
  телеметрии, уже записанной в SQLite.
- `POST /telemetry/validate` — валидация payload формата `telemetry.v1`.
- `POST /telemetry` — запись валидной телеметрии в SQLite.

## Команды разработки

```bash
make help
make test
make lint
make dev
make check
make build
make test-api
```

`make test-api` использует локальную `test`-группу `apps/api`. Общие тестовые входы
находятся в корневом `conftest.py` и не импортируют UI.
Ruff настроен на минимальный поддерживаемый Python 3.11, а не на синтаксис 3.14.

Dev-серверы Vite используют отдельные кеши `apps/web/node_modules/.vite-<port>`.
Для параллельной проверки задавайте другой порт через `--port` и сохраняйте
`--strictPort`: стенд не должен перезаписывать кеш React основного сервера.
После изменения конфигурации кеша полностью обновите ранее открытую вкладку.

`make ingest` сохраняет legacy-импорт телеметрии ДНС-7с, но сейчас требует
недоступных внешних файлов. Для новых выгрузок используются согласованные
форматы телеметрии и их проверки; произвольные инженерные Excel/Word не импортируются.

### Ручной перенос инженерных данных

Изменения характеристик вносятся отдельными записями через `#equipment-journal`
и сохраняются в SQLite. `config/plants/<id>.yaml` остаётся начальным вводом объекта
и источником исходного выездного режима. Оборудование на момент расчёта собирается
из базовых паспортов и независимых изменений журнала, а не берётся из YAML.

Для контрольного замера указывается известная дата `measured_at`: позднее
полученное уточнение плотности не подставляется в более ранний режим.
У старых YAML поле `source` необязательно. Для новых записей журнала источник
и автор обязательны; отчёт энергоаудита не требуется.
Подробности вроде листов и ячеек можно сохранять для разовой проверки рядом с
исходным артефактом, но они не являются обязательными входами расчёта.
Единицы сверяются явно, КПД в процентах переводится в доли.

Отдельного импортёра инженерных отчётов и команд генерации паспортов из них нет.
Расчётное ядро и его тесты работают со структурированными входами, не угадывая
смысл таблиц. Сохранённые ранее YAML/JSON и результаты сверок не становятся
подтверждёнными только из-за успешного чтения схемы: наследованные данные требуют
ручной проверки. Неподтверждённые параметры не заменяются догадками.

Для существующих объектов правка YAML не заменяет сведения SQLite. Вносите только
изменяемые параметры через журнал с подходящей датой действия; история сохраняется.

### Характеристики из материалов Рамиля

Коэффициенты и точки характеристик проверяются вручную по источнику перед
внесением в паспорт. Одноразовый CLI разбора листа «Уравнения» удалён;
результат прежней проверки сохранён для ручного рассмотрения.
Снимок результата: `data/reference/cns40-1000-2-review.json`. Это кандидат
со статусом `approval: pending`, а не утверждённый паспорт. До подключения к
рабочему расчёту требуется подтвердить исполнение, частоту и применимость
коэффициентов; отдельно согласовать рекомендуемую рабочую область:
таблица рекомендаций A-2026-023 задаёт верхнюю границу 48 м³/ч,
а лист «Уравнения» — область 28–60 м³/ч. Происхождение коэффициентов
(испытания или оцифровка паспортного графика) также требует подтверждения.
Q–η сравнивается отдельно, без изменения принятой декомпозиции потерь КНС.


### Адресная диагностика по таблицам КНС

В «Машинном блоке» и «Режимном расчёте» React
показаны проверки из A-2026-023 (`Таблицы по КНС.xlsx`). Привязки к объекту,
агрегату, модели, листу и строкам находятся в `config/diagnostics.yaml`.
Оба ответа API — `field-trip-audit` и `snapshot-audit` — содержат `diagnostics`.
Для каждой проверки доступны условие, значения с единицами и основанием,
действие для проверки, SHA-256 исходного документа и точные ячейки.
Используются заголовки блоков источника: подписи «НА-1», скопированные
в отдельные строки других агрегатов, не меняют привязку к оборудованию.

Проверки разделены на согласованность данных, отклонения режима и основания
для обследования. Статусы различают обнаруженный признак (`triggered`),
необнаруженное условие (`clear`), нехватку данных (`insufficient_data`),
неподтверждённое основание (`pending_confirmation`) и отсутствие привязки
(`not_applicable`). Ни один из них не является диагнозом или командой управления;
`clear` не означает исправность всего агрегата.

Для совпадающих привязок проверяются порядок давлений БГ/выкида и загрузка ЭД
(строгие границы `< 0,5` и `> 1`). Противоречие `pБГ > pвых` в выездном режиме
делает экономические выводы недоступными. По потерям доступны только признаки
для обследования, без команды открыть задвижку или заменить насос.
Годовые признаки не выводятся при предположительной годовой наработке.
Суточный УРЭ не сравнивается с расчётным по одному снимку давления;
среднесуточный КПД не подменяется КПД выбранного режима.

Неподтверждённые рабочие области, Q–H/Q–η и неоднозначные «20 атм»/«5% КПД»
видны в ограничениях, но не генерируют рекомендации. Для КНС-97 привязка
всего блока требует подтверждения: ЦНС 40-1000(-2) назван НА-1 в источнике,
а в системе — НА-2 ПР. Совпадение модели не разрешает перенос правил
между агрегатами. Смена модели в паспорте блокирует прежние правила.
Другие объекты без профиля не получают чужие пороги.

Страница «Машинный блок → Рекомендации» показывает тот же отчёт диагностики и
справочные сведения к нему: бенчмарки насосов и ЭД, рабочую область ЦНСн из
приложения к «Алгоритму определения критичных параметров НА», журнал дефектов
1С ТОИР с вероятными причинами по алгоритму (`config/toir.yaml`). На странице
статьи карты потерь (клик по столбцу) выводятся относящиеся к статье правила.
Справочник правил и привязок — «Данные и методика → Справочник».

### Приёмка поступившей телеметрии

На странице «Телеметрия» перед графиками доступен отчёт «Приёмка данных»
за тот же выбранный период. API:
`GET /objects/{object_id}/telemetry-acceptance?aggregate_id=…&start=…&end=…`.
Отчёт только читает БД: импорт, паспорта и расчётные характеристики не меняются.

Для ожидаемых и дополнительных сигналов показаны единицы, число записей,
число прошедших входные проверки, первая/последняя пригодная запись,
дни с ними и максимальный интервал между ними. Без нормативной частоты
опроса этот интервал не называется пропуском или процентом полноты.
Неизвестные метки качества выводятся буквально и не считаются подтверждёнными.
Отрицательные/неконечные значения, неподходящие единицы и неоднозначные
записи на один момент исключаются из проверки полноты. Суточные наработки
выше 24 ч и нулевая плотность также исключаются.

«Суточный УРЭ W/Q» требует однозначных итогов энергии и положительного объёма
одного агрегата за одни сутки. Итоги станции не подменяют итоги агрегата.
Число совместных суток относится только к доступной части периода.
«Синхронный набор для мгновенного режима» проверяет наличие положительных
p_in/p_out/power/flow_rate/density на один момент, без переноса значений.
Это намеренно более строгая проверка сырых входов, а не замена обработки
давлений-состояний расчётным ядром. Доступность набора не означает
готовность аудита: паспорт, физическая согласованность, экономика и
годовая экстраполяция требуют отдельных проверок.
