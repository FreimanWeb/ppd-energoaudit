# Цифровая модель энергоаудита ППД

Прототип цифрового энергоаудита насосных агрегатов ППД. Он объединяет паспортные
данные, телеметрию и расчёт по выездному замеру. Расчётные формулы соответствуют
Методике энергоаудита (формулы 7–47); ограничения и допущения выводятся в UI.

## Монорепо и новый frontend

В одном репозитории находятся:

- `src/ppd_audit/` — общее Python-ядро, работа с данными и FastAPI;
- `frontend/` — React + TypeScript + Vite, отдельный npm workspace;
- `shared/ppd-symbols.svg` — общие изображения оборудования для React и Streamlit;
- `app/` — рабочий Streamlit-интерфейс, сохраняемый на время перехода;
- `config/` и `tests/` — описания объектов и Python-проверки.

React содержит все активные разделы прежнего интерфейса: обзор, режимный расчёт,
телеметрию, прогноз закачки, CRM по агрегатам и скважинам, схему ППД, карту потерь,
рабочую точку, мероприятия, подключение объекта и формулы. Дополнительный раздел
показывает источники данных. Боковая панель содержит фильтры воды/НГДУ, объект,
агрегат, календарь пригодности и общий момент измерения. Параметры анализа
расположены над разделами; на desktop навигация прокручивается отдельно.
Объект, агрегат, дата, момент и режим сохраняются в query-параметрах URL
(`object`, `aggregate`, `day`, `timestamp`, `mode`), раздел — в hash. Ссылку
можно открыть в другой вкладке или передать коллеге; обновление страницы и
Back/Forward восстанавливают выбранный контекст. При изменении селекторов
текущая запись history обновляется без добавления шага на каждый выбор.

Оба интерфейса используют одно Python-ядро и общие `services`: каталог и исходные
данные, прогноз, кривые насоса, экономика, требования к данным и типографика формул.
React получает расчётные значения через API. Подключение объекта остаётся справкой
с требованиями и шаблонами конфигурации; создание и редактирование паспортов через
браузер не предусмотрено прежним интерфейсом.

Для разработки нужны Node.js 22.12+ и `uv`. Установка из корня монорепо:

```bash
uv sync --frozen --extra api --extra dev
npm ci
```

В первом терминале запустите API:

```bash
npm run dev:api
```

Во втором — frontend:

```bash
npm run dev
```

Frontend открывается на `http://127.0.0.1:5173`, API — на
`http://127.0.0.1:8000`, OpenAPI — на `http://127.0.0.1:8000/docs`.
Vite направляет `/api/*` в FastAPI, поэтому для локального запуска отдельная
настройка CORS не требуется. Этот запуск предназначен для локальной разработки. Авторизация поддерживается
в обоих интерфейсах: пароль берётся из `PPD_APP_PASSWORD` либо
`.streamlit/secrets.toml` (`app_password`). Без настроенного пароля вход свободный.
API выдаёт подписанную HttpOnly cookie `ppd_session` сроком на 8 часов; logout
удаляет её. Для нескольких backend workers задайте одинаковый
`PPD_SESSION_SECRET` длиной не менее 32 байт. Для HTTPS задайте
`PPD_COOKIE_SECURE=1`. Reverse proxy должен перезаписывать `X-Forwarded-Host`
реальным внешним host; Vite делает это автоматически.

API использует существующий `telemetry.sqlite`; альтернативный путь задаётся
через `PPD_DATABASE_PATH` перед `npm run dev:api`. Импорт телеметрии остаётся
отдельной операцией: новый frontend не подставляет выездной расчёт при отсутствии
измерений.

```bash
npm run typecheck
npm run test:frontend
npm run build
.venv/bin/python -m pytest
npm run test:e2e
```

Browser-проверки поднимают отдельные FastAPI/Vite на портах 8181/5181 и
8191/5191, создают временную SQLite и собственные CSV/XLSX источники. Рабочие
данные не изменяются. Установите Chromium через
`npm exec --workspace frontend playwright install chromium` либо задайте
`PLAYWRIGHT_CHROMIUM_EXECUTABLE` путём к установленному Chromium.

Сборка сохраняется в `frontend/dist`. Для её публикации нужен сервер, который
раздаёт файлы и направляет `/api/*` в backend; dev proxy в сборку не входит.

## Текущее состояние данных

- `telemetry.sqlite` в корне — локальная SQLite-БД приложения. Она хранит объекты,
  НГДУ, паспорта, уточнения и нормализованную телеметрию. Файл намеренно не
  коммитится: при необходимости он передаётся отдельно.
- `config/plants/*.yaml` — исходные паспорта и статичные выездные замеры. При первом
  запуске БД заполняется из них; после этого режим телеметрии читает данные из SQLite.
- `data/raw/ntu` — symlink на внешнюю папку «НТУ цифровая платформа». Он не переносим
  между рабочими местами и не является обязательным для работы Streamlit-приложения.
- ДНС-7с оставлена как legacy-верификационный пример. Ссылки на её Excel-файлы сейчас
  битые, поэтому в текущей SQLite-БД для ДНС-7с нет телеметрии. Не используйте
  `make ingest`, пока исходные файлы не будут получены заново.

## Быстрый запуск

```bash
uv sync --extra app --extra api --extra dev
uv run streamlit run app/main.py
```

Для backend API:

```bash
uv run uvicorn ppd_audit.api.main:app --reload
```

По умолчанию приложение использует `telemetry.sqlite` в корне. Для другого файла
задайте `PPD_DATABASE_PATH` перед запуском API. Если БД отсутствует, приложение
создаст её и перенесёт паспорта из `config/plants/`; телеметрия автоматически не
импортируется.

## Режимы обоих интерфейсов

- **Анализ** — расчёт по телеметрии SQLite за выбранные сутки. Сначала выбирается
  пригодный режимный снимок: устойчивая пара `p_вх`/`p_вых`, согласованная с
  положительной мощностью. Если данных недостаточно, приложение показывает причину,
  а не подставляет выездной расчёт.
- **Выезд** — статичный расчёт по YAML-паспорту и выездному замеру. Календарь,
  телеметрия и индикаторы её наличия в этом режиме не используются.
- **Просмотр телеметрии** — графики исходных точек за выбранный период без расчёта KPI.

В режиме «Анализ по телеметрии» `🟢` означает, что хотя бы у одного агрегата объекта
есть записи телеметрии, `⚪` — что их нет. Это не оценка пригодности конкретной даты.

## Модель данных

SQLite содержит:

- объект, НГДУ, тип воды и ветку расчёта;
- технические места и агрегаты;
- версии паспортов насоса, двигателя и трансмиссии;
- временные ряды `p_вх`, `p_вых`, `p_БГ`, мощности, расхода, энергии, наработки и
  других метрик;
- временные значения, требующие уточнения.

`p_вх`, `p_вых` и `p_БГ` хранятся как события изменения: строка появляется только
при новом значении, а до следующего события действует последнее записанное значение.
Отсутствие строки не означает отсутствие данных. Мощность дискретна с шагом 30 минут;
пропущенный слот также означает сохранение предыдущего значения. SQLite хранит только
исходные события, а расчёт восстанавливает действующее состояние в выбранном окне.

Для КНС `p_БГ` — станционная метрика напорного коллектора. Она не заменяет
`p_вых` конкретного насоса: в расчёт допускаются только физически корректные снимки
с `p_вых > p_вх` и, при наличии `p_БГ`, с `p_вых > p_БГ`.

## Источники и ограничения

Тестовые временные ряды в текущей БД относятся к КНС-10, КНС-54, КНС-ОПУ и КНС-97.
Наличие записи не означает, что по ней возможен полный расчёт: требуются паспорт,
подача, мощность и согласованные давления. Режим «Выезд» доступен и для объектов
без телеметрии, если YAML содержит измеренный режим.

Файлы `…расчет.xlsx` и текстовые отчёты остаются источниками исторической сверки,
но не требуются для обычного запуска приложения. Их пути могут ссылаться на внешнюю
папку данных и потому не считаются частью переносимого прототипа.

## API

Дополнительные источники можно задать через `PPD_CRM_DIR`,
`PPD_DOWNTIME_DIR`, `PPD_SCADA_TAGS_PATH`; без них используются каталоги проекта.
Полные схемы запросов и ответов доступны в OpenAPI.

- `GET /auth/session`, `POST /auth/login`, `POST /auth/logout` — состояние входа,
  вход с `{ "password": "..." }` и выход.
- `GET /catalog/objects` — каталог объектов с наличием телеметрии; прежний
  `GET /objects` сохраняет свой контракт.
- `GET /objects/{object_id}/telemetry?aggregate_id=&start=&end=` — события и
  подготовленные ряды за период включительно (`start/end`: `YYYY-MM-DD`).
- `GET /objects/{object_id}/aggregates/{aggregate_id}/calendar?month=YYYY-MM`
  — пригодность суток.
- `GET /objects/{object_id}/aggregates/{aggregate_id}/forecast?start=&end=&period_days=&horizon=`
  — история и прогноз; период 1/7/30 суток, горизонт до 3660 периодов.
- `GET /objects/{object_id}/crm/runs`, `/crm/runs/{code}`, `/crm/fact`
  — прогоны, прогнозы агрегатов и фактическая закачка.
- `GET /objects/{object_id}/crm/well-runs`, `/crm/well-runs/{code}`,
  `/crm/well-runs/{code}/graph` — месячные прогнозы скважин и граф связей.
- `GET /objects/{object_id}/crm/well-runs/{code}/monthly?well=` — выбранный
  месячный ряд, временное окно и отметки простоев, общие с Streamlit.
- `GET /objects/{object_id}/well-downtime`, `/clarifications?aggregate_id=`
  — простои скважин и временные паспортные значения.
- `GET /objects/{object_id}/scheme-pressures?day=&timestamp=` — давление каждой
  ветки на общем моменте; отсутствующие снимки не заменяются чужими значениями.
- `POST /objects/{object_id}/aggregates/{aggregate_id}/field-trip-audit`
  — выездной аудит из YAML, без выдуманного телеметрического снимка.
- `POST /objects/{object_id}/aggregates/{aggregate_id}/working-point`, `/measures`
  — характеристики и экономика; контекст `source: telemetry|field_trip`,
  для телеметрии обязательны `day` и `timestamp`.
- `GET /objects/{object_id}/aggregates/{aggregate_id}/onboarding`
  — требования, полнота паспорта и шаблоны.

- `GET /health` — healthcheck.
- `GET /objects` — объекты из SQLite.
- `GET /objects/{object_id}/aggregates` — агрегаты объекта и наличие телеметрии.
- `GET /objects/{object_id}/aggregates/{aggregate_id}/dates` — доступные даты
  и дата первоначального выбора.
- `GET /objects/{object_id}/aggregates/{aggregate_id}/snapshots?day=YYYY-MM-DD`
  — пригодные режимные снимки выбранных суток.
- `GET /objects/{object_id}/topology` — описание технологической схемы либо
  явно обозначенная типовая цепочка по реальным агрегатам.
- `POST /objects/{object_id}/aggregates/{aggregate_id}/snapshot-audit`
  — аудит точного снимка; тело `{ "day": "YYYY-MM-DD", "timestamp": "..." }`.
  Ответ содержит показатели, качество, источники параметров, расчётное основание
  годовых оценок и статьи потерь. Для непригодных режимов статьи потерь не выдаются.
- `POST /energy/audit` — расчёт по переданному `ObjectSpec`.
- `POST /objects/{object_id}/aggregates/{aggregate_id}/audits` — расчёт по окну
  телеметрии, уже записанной в SQLite.
- `POST /telemetry/validate` — валидация payload формата `telemetry.v1`.
- `POST /telemetry` — запись валидной телеметрии в SQLite.

## Команды разработки

```bash
make help
make test
make lint
make app
make api
make verify
```

`make verify` и `make reports` требуют исходные расчётные файлы и отчёты во внешней
папке `data/raw/ntu`. `make ingest` сейчас намеренно не является воспроизводимой
командой: ему нужны недоступные файлы ДНС-7с.
